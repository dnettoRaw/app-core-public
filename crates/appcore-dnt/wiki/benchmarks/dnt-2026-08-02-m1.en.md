# DNT Benchmark: Apple M1, 2026-08-02

Status: observed local evidence for commit ancestry at the time of the run. It
is not cross-platform certification and must be regenerated on deployment
hardware.

## Environment

- Command: `cargo run --release -p appcore-dnt --example compare`.
- Hardware: MacBook Pro `MacBookPro17,1`, Apple M1, 8 cores, 16 GB RAM.
- OS/kernel: macOS, Darwin 27.0.0, aarch64.
- Storage: internal solid-state storage, APFS.
- Power: AC power, battery charged.
- Rust: `rustc 1.97.1 (8bab26f4f 2026-07-14)`.
- Cargo: release profile, default features.
- Execution: one thread; 20 warm-up operations for each path.
- Samples: 200 for read/open; 100 for seal/rekey.
- Read cache: warm. Results are not durable-I/O or cold-cache measurements.
- CPU time, peak RSS and per-operation allocations: not measured.

Throughput below uses semantic plaintext bytes, so compact throughput reflects
useful payload returned rather than encrypted bytes read from disk.

## Interpretation

The plaintext read is a performance baseline only. It provides none of DNT's
confidentiality, AEAD authenticity, authenticated routing metadata, application
and tenant binding, key rotation or versioned migration.

Compact JSON is faster than normal DNT in this run because compression reduced
the bytes processed by XChaCha20-Poly1305 and the keyed payload digest from
about 1 MiB to about 4 KiB. Inflating the result was cheaper than authenticating
the additional ciphertext. This is data-dependent, not a general compression
guarantee: incompressible binary became slightly larger and slower, while a
small secret paid pure wrapper overhead.

Normal DNT remains the default. Compact mode is appropriate only after the
caller has considered payload entropy, size leakage and decompression limits.
The V1 normal 1 MiB open p95 of 5.80 ms on this machine is below the initial
10 ms desktop target, but no conclusion is made for Raspberry Pi, Windows,
Linux, cold storage, concurrency or durable I/O.
